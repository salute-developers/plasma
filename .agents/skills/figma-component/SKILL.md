# Реализация компонента по Figma или Pixso

Использовать этот skill, чтобы превратить конкретную ноду Figma или Pixso в компонент Plasma или точечные изменения существующего компонента без догадок о дизайне.

## Целевой пакет

Пользователь может явно указать пакет для сверки/правок (например, `plasma-b2c`, `plasma-giga`, `sdds-serv`, `sdds-insol-next`) в тексте запроса.

1. Если в запросе явно назван пакет (имя пакета из `packages/*`, путь вида `packages/{pkg}/...` или формулировка вроде "в пакете X", "для X"), использовать именно этот пакет как целевой и не выполнять автопоиск по остальным `packages/*`. Если указанного пакета или компонента в нём не существует, сообщить об этом и уточнить у пользователя, прежде чем продолжать.
2. Если пакет не указан, действовать как раньше: искать целевой пакет автоматически по правилам из раздела "Изучение репозитория".

## Получение макета из Figma или Pixso

Определить источник по ссылке или явному указанию пользователя. Найти инструменты соответствующего провайдера среди доступных tools либо через tool discovery, если он доступен. Не передавать Pixso-ссылки в Figma MCP и не переносить схему его аргументов на Pixso.

### Figma

1. Извлечь `fileKey` и `nodeId` из Figma URL; преобразовать `node-id=123-456` в `123:456`.
2. Если конкретного `node-id` нет, запросить ссылку на точную ноду до реализации.
3. Перед `get_design_context` прочитать `figma:figma-design-to-code`, если этот навык доступен; выполнить обязательные инструкции используемого инструмента.
4. Вызвать Figma MCP `get_design_context`, затем `get_screenshot` для тех же `fileKey` и `nodeId`.
5. Если нужны дополнительные свойства потомков, прочитать их через Figma MCP/Plugin API; перед `use_figma` прочитать доступный навык `figma:figma-use`.

### Pixso

1. Использовать ссылку на конкретный слой с `item-id`. Для Local MCP допустимо явно указанное пользователем текущее выделение: сначала проверить целевой файл и выбранную ноду через доступный инструмент. Если цель неоднозначна, запросить ссылку на слой до реализации.
2. Сохранять Pixso URL и идентификаторы в формате, который принимает подключённый инструмент. Не применять преобразование Figma `123-456` → `123:456` к Pixso.
3. Проверить фактически доступные инструменты и их схемы: набор зависит от версии и подключения Local/Remote MCP. Для Local MCP целевой файл должен быть открыт и активен в работающем клиенте Pixso.
4. Получить структуру и свойства точной ноды через доступный инструмент чтения, например `get_node_dsl`; при необходимости дочитать потомков. Получить скриншот той же ноды через доступный `get_screenshot` или `take_screenshot`. Экспорт отдельного asset не считать скриншотом всего макета.
5. При необходимости дополнить данные доступными средствами чтения компонентов, вариантов, стилей и переменных. Не предполагать, что краткий DSL или сгенерированный код содержит все instance properties и text styles.

Справка Pixso: [инструменты MCP](https://pixso.net/developer/zh/mcp/tools.html), [Local MCP](https://pixso.net/developer/en/mcp/local-mcp.html), [Remote MCP](https://pixso.net/developer/en/mcp/remote-mcp.html). Конкретные вызовы и аргументы брать из схем подключённых tools.

### Полнота данных

Для обоих источников нужны структура, размеры, отступы, стили, свойства компонентов и визуальный образец одной и той же ноды. Любой сгенерированный HTML/React/Tailwind использовать только как справочник; реализацию адаптировать к Plasma и проекту.

Если MCP недоступен или не раскрывает нужные данные, явно назвать ограничение. Использовать предоставленные пользователем экспорт структуры/свойств и скриншот той же ноды; запросить недостающее, если оно влияет на реализацию. Скриншот не заменяет instance properties, variants, text styles или привязки токенов. Продолжать независимое изучение репозитория, но не угадывать отсутствующие значения и не объявлять непроверенную сверку завершённой.

## Выбор сценария

После получения контекста макета определить сценарий:

1. **Правка существующего компонента**: компонент уже есть в целевом пакете или в `plasma-new-hope`; нужно сравнить его с макетом и внести минимальные правки.
2. **Новый компонент по существующему дизайну**: подходящего компонента нет; нужно создать новый компонент, используя ближайшие существующие паттерны репозитория.

Если компонент похож на существующий, но отличается назначением или API, сначала проверить, можно ли выразить дизайн через props/config существующего компонента. Новый компонент создавать только когда переиспользование приведет к неестественному API, ломким overrides или смешению разных сущностей.

## Изучение репозитория

Перед правками:

1. Найти целевой пакет и компонент:
    - Если пакет уже определен в разделе "Целевой пакет" (явно указан пользователем), искать компонент сразу в `packages/{pkg}/src/components/{Component}`, без перебора остальных пакетов.
    - Иначе искать существующие папки компонентов в `packages/*/src/components/{Component}`.
    - Проверять, живет ли общий примитив в `packages/plasma-new-hope/src/components/{Component}`.
    - Если компонент не найден, определить ближайшие аналоги по layout, слотам, токенам, интерактивности и story/test структуре.
2. Прочитать файлы компонента:
    - `{Component}.config.ts`
    - `{Component}.ts` или `{Component}.tsx`
    - `{Component}.stories.tsx`
    - component tests, если они есть
    - связанные shared tokens/styles/types в `plasma-new-hope`
    - для нового компонента: такие же файлы у 1-3 ближайших аналогов
3. Найти похожие компоненты или варианты в других пакетах до создания новых абстракций.
4. Сохранять публичный API и существующие паттерны, если макет явно не требует нового prop или нового компонента.
5. Для нового компонента проверить локальные export conventions:
    - `packages/{pkg}/src/components/{Component}/index.ts`
    - `packages/{pkg}/src/index.ts`
    - наличие `*.config.ts`, `*.stories.tsx`, `*.component-test.tsx` или `*.update-test.component-test.tsx` у соседних компонентов.

## Правила маппинга дизайна

Маппить факты из макета на конструкции репозитория:

-   Типографика: использовать theme typography tokens, уже принятые в целевом пакете.
-   Цвета: использовать theme color tokens или существующие CSS variables пакета.
-   Размеры и отступы: задавать через component tokens в package config, если существующий примитив уже поддерживает эти значения.
-   Layout: переиспользовать существующие slots и props, например `contentLeft`, `contentRight`, `children`, `title`, `subtitle`, `label`, `stretching` и props выравнивания.
-   Иконки/assets: использовать существующие иконки репозитория только когда имя слоя в макете или существующая конвенция однозначно определяет иконку. Если слой называется обобщенно, например `icon`, оставить его slot-based и отметить конкретный asset как неясный.
-   Dividers/list behavior: переиспользовать существующие `List`, `Divider` или pseudo-element patterns, если такое поведение уже есть в репозитории.

Не хардкодить временные asset URLs из Figma/Pixso в исходный код. Они не подходят для реализации в package.

## Правила редактирования

Держать изменения узкими:

1. Предпочитать правки package config tokens вместо изменений shared primitive.
2. Менять shared-код `plasma-new-hope` только если целевой дизайн требует поведения, которое нельзя выразить через package config.
3. Обновлять stories, когда это самый понятный способ показать реализованное состояние дизайна.
4. Добавлять или обновлять тесты, когда меняется поведение, публичный API или visual contract.
5. Не придумывать отсутствующие детали дизайна. Добавлять короткий TODO или заметку в финальный ответ для всего, что осталось неясным.

При реализации нового компонента:

1. Выбрать базовую реализацию:
    - Если есть подходящий shared primitive в `plasma-new-hope`, создать package wrapper через `component(mergeConfig(...))` и package config.
    - Если shared primitive отсутствует, создать минимальный новый primitive в наиболее подходящем слое только после проверки соседних компонентов и exports.
2. Следовать структуре ближайшего существующего компонента в целевом пакете.
3. Назвать props по существующим conventions репозитория, а не по случайным именам слоёв макета.
4. Экспортировать компонент из `index.ts` компонента и из package `src/index.ts`, если этого требует локальная конвенция.
5. Добавлять config, stories и focused tests по образцу соседних компонентов.
    - В stories контролы, которых нет в API компонента (`enableContentLeft`, `hasHint`, ширина обёртки и т.п.), оборачивать в `exampleOnly({...})` из `@salutejs/plasma-sb-utils` — они попадут в секцию `Example only`. Пропсам компонента `table.category` не задавать.
6. Для variants из макета описывать размеры/виды через config variations и tokens, а не через ad hoc CSS в story.
7. Предпочитать wrappers/shared primitives из `@salutejs/plasma-new-hope/styled-components`, если они доступны.

## Валидация

Запускать минимальные осмысленные проверки:

1. `npm run lint --prefix packages/{target-package}` для package edits.
2. `npm run generate:typings --prefix packages/{target-package}`, если могли измениться exported component types.
3. Запускать focused Cypress/component tests, если test files были добавлены или изменены.
4. Если command не удалось запустить, сообщать точную команду и причину сбоя.

## Финальный ответ

Сообщать:

-   Источник макета (Figma/Pixso), точная нода, фактически выполненные вызовы для получения данных и скриншота либо использованные экспорты.
-   Выбранный сценарий: правка существующего компонента или создание нового компонента.
-   Измененные файлы.
-   Важные design-to-code решения.
-   Команды валидации и их результат.
-   TODO для неясных деталей макета, если они есть.

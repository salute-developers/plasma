# Workflow Metrics

Storybook-страница `Engineering / Workflow Metrics / Cypress` показывает историю Cypress из архивов v3. Корневой `WorkflowMetrics.tsx` только собирает секции страницы; загрузка, расчёты и UI находятся в отдельных модулях.

```text
WorkflowMetrics.tsx              Сборка страницы
WorkflowMetrics.stories.tsx      Storybook и адрес источника данных
ui/                             Секции страницы, график, таблицы, поля и стили
hooks/                          Состояние страницы и жизненный цикл запросов
model/                          Общие типы, конфигурация workflows, нормализация и снимок истории
archive/                        Типы чанков, валидация, дневные ряды, выборка и планирование страниц
api/                            HTTP-клиент, проверка payload и кеш неизменяемых чанков
utils/                          Даты, интервалы покрытия, статистика, форматирование и async pool
docs/                           Формат архивов и исследование исторических данных
```

## UI и состояние

-   `ui/ArchivePanel.tsx` — выбор workflow, метаданные архива, предупреждения и экспорт.
-   `ui/FiltersPanel.tsx` — период, браузер, метрика, группировка и пакеты.
-   `ui/MetricsChart.tsx` — SVG-график; `ui/ChartPanel.tsx` — подписи и таблица его значений.
-   `ui/JobsPanel.tsx` — строки последних jobs и ссылки на GitHub.
-   `ui/SummaryCards.tsx`, `ui/FilterSelect.tsx`, `ui/TablePagination.tsx` — остальные элементы страницы.
-   `ui/layout.styles.ts` — общие стили и адаптивная сетка.

`hooks/useArchiveSource.ts` управляет манифестом выбранного workflow, исходным периодом/пакетами и явным экспортом полного JSON. `hooks/useArchiveQueries.ts` загружает годовые ряды и месячные jobs, отменяет устаревшие запросы и поддерживает повтор после ошибки. `hooks/useWorkflowMetrics.ts` связывает фильтры, статистику и пагинацию, возвращая props отдельных секций страницы.

## Общие данные и сборщик

`model/index.ts` и `archive/index.ts` — общие точки входа для страницы, тестов и [GitHub action](../../../../../.github/actions/workflow-metrics/README.md). Эти модули не импортируют React, UI или hooks и доступны напрямую из Node из `.nvmrc`. В общих модулях используются явные расширения `.ts`, необходимые Node.

Внутри feature импортируйте конкретный модуль по назначению: `model/types`, `model/jobs`, `archive/validation`, `archive/series`, `utils/dates` и т. д. `api/index.ts` предоставляет клиент и инструменты выборки для его потребителей. Изменение структуры не меняет формат сохранённых архивов.

Описание формата, загрузки и S3: [ARCHIVE_V3.md](docs/ARCHIVE_V3.md). Исследование февральского выброса: [FEBRUARY_2026.md](docs/FEBRUARY_2026.md).

## Сбор и продолжение

Сбор выполняет [composite action](../../../../../../.github/actions/workflow-metrics/README.md); скрипты перенесены в `.github/actions/workflow-metrics/scripts`. npm-команд сбора в пакете больше нет. Команды ниже предназначены для отладки из корня репозитория с Node из `.nvmrc`.

```sh
# Сбор всех категорий; по умолчанию сохраняется не менее трёх календарных лет.
node .github/actions/workflow-metrics/scripts/cli/collect.mjs --require-token

# Сбор с нуля или продолжение в отдельном каталоге.
node .github/actions/workflow-metrics/scripts/cli/collect.mjs --require-token --output-dir=/tmp/workflow-metrics

# Дополнение метаданных без GitHub API: spec-файлы b2c и new-hope.
node .github/actions/workflow-metrics/scripts/cli/spec-counts.mjs
```

Для сбора задайте `GITHUB_TOKEN` или `GH_TOKEN` в окружении. По умолчанию данные записываются в `.storybook/public/workflow-metrics/v3/`. Начальный снимок включён в git. Storybook использует файлы напрямую; после обновления данных достаточно перезагрузить страницу. При сборке Storybook дополнительных преобразований нет.

`--output-dir` задаёт корень, внутри которого создаётся `v3/`. `--workflow=all` обрабатывает все категории; можно передать имя workflow, например `--workflow=cypress.yml`. При отсутствии `manifest.json` создаётся пустой архив v3. Если манифест есть, отсутствие или повреждение любого указанного чанка считается ошибкой; история не сбрасывается.

Контрольные точки записываются каждые 10 прогонов, после завершённого окна и при остановке. Пересоздаются только затронутые месяцы `jobs`/`state` и годы `series`; изменение одного `updatedAt` не пересоздаёт чанки. Порядок прогонов и jobs нормализуется по дате и ID. Код 2 означает сохранённый прогресс при ограничении API/бюджета; повторите ту же команду. Последние 7 дней перепроверяются, более старые reruns обнаруживаются увеличением `--refresh-days`. Ограничения на число лет и автоматического удаления старой истории нет.

## Структура

Для каждой категории (`daily`, `pull-requests`, `release`) создаётся каталог:

```text
manifest.json
series/YYYY.<sha256>.json
series/YYYY.<sha256>.json.gz
jobs/YYYY-MM.<sha256>.json
jobs/YYYY-MM.<sha256>.json.gz
state/YYYY-MM.<sha256>.json
state/YYYY-MM.<sha256>.json.gz
```

-   `manifest` содержит версию 3, репозиторий, workflow, диапазон, `updatedAt`, `collectionRevision`, покрытие, предупреждения, общие счётчики и пакеты. Для каждого чанка: период, относительный путь, SHA-256 несжатого JSON, размеры JSON/gzip и число записей.
-   `series` содержит дневные группы по пакету и браузеру: длительности успешных jobs с известным временем (включая нули), число успешных jobs (включая jobs без времени), ошибок и всех jobs, уникальные ID прогонов. React и исходные workflows объединяются как в текущем интерфейсе. Для spec-файлов сохраняются min/max, точность ревизии и покрытие среди jobs с известным временем.
-   `jobs` содержит полные измерения, включая ошибки, отсутствующие времена, React, ветки, источник workflow и ревизии spec-файлов. Граница определяется датой создания прогона в UTC: поздний rerun принадлежит исходному месяцу.
-   `state` содержит все прогоны, их попытки, `collectionRevision` и `headSha`, включая прогоны без Cypress jobs. Эти чанки нужны сборщику; для графика их загружать не требуется.

Периоды без записей не получают пустые чанки. Полноту сбора определяет `coverage`, а не наличие файла.

В `series` сохраняются сами длительности, а не дневные p90. После выбора UTC-дней, пакетов и браузеров p90, медиана и среднее вычисляются заново. Результат точен и для неполных недель/месяцев. Счётчики `success` позволяют определить месяцы для любой страницы таблицы без загрузки предыдущих страниц.

## Загрузка в интерфейсе

`WorkflowMetrics` принимает `dataBaseUrl` корня архивов (по умолчанию `./workflow-metrics`), к которому добавляются `/v3/<категория>/manifest.json` и пути чанков. Для внешнего S3 origin нужен CORS. Автоматического отката на монолитные JSON нет.

1. Манифест перепроверяется через `cache: no-cache`; по нему отображаются общий период, счётчики, пакеты и неполные интервалы.
2. Для графика загружаются только годовые `series`, пересекающиеся с выбранными датами. Начальный период с 01.08.2025, все пресеты и точность p90/медианы/среднего сохранены. Фильтры пакета и браузера применяются к уже загруженным дневным группам. Группировка и таблица графика не требуют подробных jobs.
3. Для страницы jobs по счётчикам `success` вычисляются нужные месяцы и смещение. Загружаются только эти месяцы; затем применяются те же фильтры и сортировка по дате/ID. Страница на границе месяцев может использовать несколько чанков. Успешные jobs без известной длительности тоже учитываются в таблице.
4. «Скачать JSON» явно загружает полные jobs и `state`, восстанавливает полный снимок `version: 3` с `runs` и `measurements` и сохраняет его в браузере. Это формат выгрузки для пользователя; сборщик хранит и читает только манифесты/чанки. При обычном просмотре `state` не загружается.

В памяти используется LRU-кеш по полному URL: до 24 файлов и 16 МиБ несжатого payload. Совпадающие запросы разделяют одну загрузку. Отмена одного потребителя не мешает остальным; при отмене всех потребителей запрос прерывается. Параллельно загружаются не более четырёх файлов на операцию. Ошибки не кешируются.

Проверяются размер файла, принадлежность workflow/периоду и структура данных; при доступном Web Crypto (HTTPS/localhost) — также SHA-256. Число отфильтрованных строк месяца сверяется с дневными счётчиками. До завершения загрузки показывается состояние ожидания; старые строки и нулевые статистики не выдаются за новый результат. Ошибки графика и таблицы имеют отдельные кнопки повтора. Смена фильтра, workflow или страницы отменяет запросы и не позволяет позднему ответу заменить текущую выборку.

## Публикация

SHA-256 вычисляется по компактному JSON с завершающим переводом строки. В чанке нет времени упаковки: смена `updatedAt` сама по себе не меняет его имя. Неизменившиеся JSON/gzip не перезаписываются.

Сначала записываются чанки и gzip-копии, затем временный файл манифеста атомарно переименовывается в `manifest.json`. Ошибка до этого шага оставляет предыдущий снимок доступным. При повторном запуске готовые объекты переиспользуются. Более новый опубликованный архив не заменяется устаревшим; каталог одного workflow нельзя перезаписать другим.

В один каталог должен писать один процесс. Cron и ручная публикация объединены в concurrency group `workflow-metrics-s3` с `cancel-in-progress: false`.

Для S3 также загружайте неизменяемые объекты первыми, манифест последним. Чанки с хешами можно кешировать надолго, манифест нужно перепроверять. Gzip-копия предназначена для загрузки под ключом `.json` с `Content-Type: application/json` и `Content-Encoding: gzip`. Наличие `.gz` рядом с JSON само по себе не включает сжатие на статическом сервере Storybook.

JSON-чанки исключены из Prettier, для них закреплён LF: форматирование меняет размер и SHA-256, даже когда значения JSON те же. Тесты проверяют соответствие JSON и gzip во всех снимках репозитория.

Старые хешированные объекты автоматически не удаляются: на них могут ссылаться предыдущие манифесты и открытые страницы. Сборку мусора нужно добавить отдельно с периодом хранения старых снимков.

## Cron и S3

Workflow: [workflow-metrics-collect.yml](../../../../../../.github/workflows/workflow-metrics-collect.yml). Расписание — `0 2 */2 * *`, то есть **05:00 МСК** по дням месяца 1, 3, 5 и далее, после старта ночного Cypress в 00:00 UTC. Доступен `workflow_dispatch`: `mode` (`collect` или `publish-existing`), `from`/`to` (пустые продолжают архив до текущего UTC-дня), категория, `refresh_days`, `max_requests`. Чтобы найти старый rerun, увеличьте окно перепроверки до его даты; `from` сам по себе не отменяет уже сохранённый `coverage`.

Исполняется код default-ветки (`dev`). Расписание заработает после включения файла в эту ветку; возможны задержки запуска со стороны Actions ([GitHub schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)). Checkout с полной историей даёт скрипту подсчёта spec-файлов доступ к локальным SHA; удалённые PR-коммиты, отсутствующие в git, не восстанавливаются автоматически. Сборка пакетов и установка npm-зависимостей не требуются: используются Node из `.nvmrc` и `s3cmd==2.4.0`.

Для первой загрузки архива из репозитория выберите **Actions → Collect Cypress workflow metrics → Run workflow → dev → mode: publish-existing**. Runner должен получить полный `v3/` через checkout. Этот режим проверяет исходные архивы и публикует их без GitHub API, подсчёта spec-файлов и PAT; используются только AWS-секреты. Идентичный повтор не пишет объекты, отличающийся снимок в S3 вызывает ошибку до публикации. Подробности и локальная загрузка без коммита — в [README action](../../../../../../.github/actions/workflow-metrics/README.md).

Последовательность режима `collect`:

1. Прочитать три манифеста из `s3://${AWS_S3_BUCKET_2}/workflow-metrics/v3/`, загрузить только указанные чанки и проверить SHA-256/счётчики/ряды. Сжатые объекты распаковываются для локального сборщика. Если конкретного манифеста ещё нет, использовать соответствующий снимок из репозитория. Ошибки авторизации, сети, бакета или целостности останавливают запуск.
2. Собрать новые прогоны и продолжить неполные интервалы. Используется PAT из обязательного repository secret `WORKFLOW_METRICS_TOKEN`, переданный сборщику как `GITHUB_TOKEN`; бюджет — 4500 запросов. Обычный лимит PAT — [5000 запросов/час на пользователя](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#primary-rate-limit-for-authenticated-users), включая другие обращения с токенами этого пользователя; фактическая квота проверяется сборщиком. Встроенный токен Actions для сбора не подставляется.
3. Дополнить spec-файлы b2c для всех категорий по git. По `dev` допускается только явно отмеченная приблизительная оценка scheduled-прогонов; для PR и release нужны доступные точные SHA.
4. Проверить локальные снимки. Загрузить новые gzip-объекты под ключами `.json`: `Content-Type: application/json`, `Content-Encoding: gzip`, `Cache-Control: public,max-age=31536000,immutable`. Неизменившиеся пути пропускаются. Объекты, на которые ссылался старый манифест, не удаляются.
5. Перепроверить, что манифест в S3 не изменился с начала запуска, и опубликовать новый с `Cache-Control: no-cache`. Публикация атомарна для каждой категории; три категории имеют независимые манифесты. Сбой до замены манифеста оставляет старый снимок читаемым. Проверка конфликта дополняет очередь workflow, но не заменяет распределённую блокировку: внешние писатели должны использовать ту же очередь.

Код сбора **2** допускает публикацию частичного прогресса и успешное завершение workflow; следующий запуск продолжает с сохранённых `state`/`coverage`. Код **1** также допускает публикацию согласованных контрольных точек, после чего workflow завершается с ошибкой. Сбой подсчёта spec-файлов не препятствует попытке сохранить уже собранные данные. Ошибка проверки архива или выгрузки приводит к ошибке job. Результаты и число выгруженных чанков выводятся в Actions Summary. Отмена/жёсткий timeout job могут прервать публикацию; предыдущие манифесты остаются доступными.

Для режима `collect` создайте repository secret `WORKFLOW_METRICS_TOKEN`: Settings → Secrets and variables → Actions → New repository secret. В качестве значения укажите fine-grained PAT с доступом к `salute-developers/plasma` и разрешением `Actions: Read-only`. Наличие непустого секрета проверяется до восстановления S3; отсутствие секрета останавливает job с указанием его имени. Значение токена не выводится.

Используются существующие секреты деплоя документации: `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_ENDPOINT`, `AWS_REGION`, `AWS_S3_BUCKET_2`, а также Signature V2. Учётные данные передаются в приватный временный config `s3cmd` с правами `0600`; значения не попадают в аргументы команд, JSON и Summary. Права учётной записи должны разрешать чтение и запись префикса `workflow-metrics/`.

Команды для отдельного запуска (реально обращаются к S3; `--output-dir` и `--baseline-dir` должны ещё не существовать при restore):

```sh
node .github/actions/workflow-metrics/scripts/cli/sync.mjs --mode=restore --output-dir=/tmp/metrics-job --baseline-dir=/tmp/metrics-baseline
node .github/actions/workflow-metrics/scripts/cli/collect.mjs --require-token --output-dir=/tmp/metrics-job
node .github/actions/workflow-metrics/scripts/cli/spec-counts.mjs --output-dir=/tmp/metrics-job
node .github/actions/workflow-metrics/scripts/cli/sync.mjs --mode=publish --output-dir=/tmp/metrics-job --baseline-dir=/tmp/metrics-baseline
```

`--bootstrap-dir` задаёт альтернативный корень начального снимка с подкаталогом `v3/`; по умолчанию он берётся из репозитория. `--mode=publish-existing` выполняет первую загрузку готового архива без сбора; существующий другой снимок в S3 не заменяется. `WORKFLOW_METRICS_S3_PREFIX` позволяет переопределить `workflow-metrics` при отдельной ручной публикации. Рабочие каталоги и baseline принадлежат одному запуску; удалите их либо задайте новые пути для следующего restore.

В PR и общих деплоях Storybook задан `STORYBOOK_WORKFLOW_METRICS_URL=/workflow-metrics`: архивы общие для всех превью и обновляются без пересборки. До первой успешной публикации этот URL недоступен. Локальная сборка без переменной использует включённый в git снимок. Для другого хоста задайте абсолютный URL и CORS на стороне хранилища/прокси. HTTP-сервер должен сохранять заголовки `Content-Encoding`/`Cache-Control` из S3. Обычный static server Storybook не применяет `.gz` автоматически.
